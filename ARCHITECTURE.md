# Architecture

This is a domain-oriented TypeScript service rather than a frontend application, so traditional Feature-Sliced Design is not a useful fit. The current folders are kept stable while dependency direction is improved incrementally:

- `domains/` contains memory, project, and retrieval data contracts.
- `normalizers/`, `parsers/`, and `indexing/` implement application workflows.
- `repositories/` and `embeddings/` contain infrastructure adapters.
- `search/` is the application retrieval service.
- `mcp/` and `cli.ts` are interface adapters and composition roots.

The intended dependency flow is interfaces -> application -> domain, with infrastructure supplied through constructors at the composition root. MCP handlers only translate tool input/output and delegate search behavior.

## Composition

`src/app/compositionRoot.ts` constructs the production graph:

1. `DatabaseConnection` and repository adapters
2. `EmbeddingsProvider`
3. `IncrementalIndexer` and `VectorRetriever`
4. `MemorySearch`, writer, archiver, and summarizer
5. `MCPToolRegistry` and `MCPServer`

MCP, CLI indexing, and the watcher entrypoint all consume this graph. Compatibility exports remain for older library callers, but production entrypoints do not depend on those global instances.

Tests construct the same search graph with `TestEmbeddingsProvider`, so they do not require a running Ollama service.

## Path contract

`MemoryMetadata.filePath` is project-relative and is exposed to retrieval and formatters. `MemoryDocument.sourcePath` is absolute and is used only for filesystem reads and incremental index state. Keeping these distinct prevents process working-directory changes from breaking indexing.

## Remaining work

The memory writer is exposed through the `memory_store` MCP tool. It writes Markdown and explicitly indexes the affected project before returning. The standalone watcher also owns its handles and closes them on `SIGINT`/`SIGTERM`.

Global search is implemented as a retriever concern: the query embedding is generated once and applied to each existing project table. Results retain project identity and are merged using project-qualified paths.

Importance is stored as normalized metadata from frontmatter and affects ranking by at most `0.1` distance units. Raw vector distance remains exposed as the result score.

Archived memories are represented explicitly in metadata and excluded by default at the application search boundary. Callers can opt in with `includeArchived`; legacy rows without the field are treated as active.

Freshness filtering is also read-only: `maxAgeDays` compares indexed file modification timestamps to the current time and leaves archival mutation to an explicit writer operation.

`MemoryArchiver` provides that explicit mutation through the `memory_archive_stale` MCP tool. It updates only old Markdown files, reports relative paths, and triggers project reindexing after the write.

Relationships currently use lightweight `relatedTo` identifiers in memory metadata. This keeps ADR and bug-history links portable across projects without introducing a graph database; reverse traversal remains future work.

Retrieval also removes highly similar result text with a conservative token-set similarity check. This reduces repeated context without pretending that lexical overlap is a full semantic deduplication model.

The next larger feature area is cross-project intelligence beyond retrieval: relationships, semantic deduplication, summaries, and importance/aging policies.

Project summaries are deterministic metadata reports generated by `ProjectSummarizer`; they do not require an LLM or leak LanceDB structures into Markdown.
